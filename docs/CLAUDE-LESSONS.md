> 이 문서는 **마트노트뿐 아니라 앞으로의 모든 앱 개발**에 적용된다.
> 새 프로젝트를 시작할 때 Claude는 이 문서를 먼저 읽고, 같은 실수를 반복하지 않는다.

## 교훈 1 — 플랫폼/API 탓하기 전에 "API 계약(특히 콜백 타이밍)"부터 확정하라

### 사례 (2026-05-18, 마트노트 위젯 "홈 화면에 추가")

**요구**: 위젯 사이즈 picker에서 크기 선택 → 런처의 "홈 화면에 추가" 팝업 → "추가"를 누르면 홈화면으로 이동해서 방금 배치된 위젯이 보이게.

**환경**: Android / Jetpack Glance·AppWidget / 삼성 One UI 8 / Galaxy S24+ (SM-S926N)

### ❌ 내가 했던 잘못된 시도

1. picker의 클릭 핸들러에서 `requestPinAppWidget` 호출 **직후 즉시** `Intent.ACTION_MAIN + CATEGORY_HOME` 로 홈 점프
   → 삼성 팝업이 **뜨기도 전에** 앱이 백그라운드로 가서 팝업이 소멸. 사용자 눈에는 "앱이 튕기기만 함".
2. 실패 원인을 **"삼성 One UI라 팝업이 막힌다 / One UI 버전마다 동작이 다르다"** 는 식의 근거 없는 플랫폼 불확실성으로 둘러댐.
3. "로그 떠보자"며 재현·빌드 왕복을 반복 → 사용자 시간 낭비. 사용자가 "이렇게 되는 건데 왜 자꾸 API 없다고 핑계대냐"고 지적함.

### ✅ 정답 (사실 단순했다)

- `AppWidgetManager.requestPinAppWidget(provider, null, successCallback)` 의 **3번째 인자 `successCallback`(PendingIntent)** 는 **사용자가 "추가"를 눌러 위젯이 실제로 배치된 바로 그 순간에만** 호출된다. → **API 26(Android 8)부터 표준. One UI도 당연히 지원. "API가 없던" 적은 단 한 번도 없었다.**
- 그 콜백을 받는 BroadcastReceiver에서 홈화면 이동 Intent를 발사 → **타이밍 경쟁 자체가 없음.**
- picker는 핀 요청 후 **앱에 그대로 머물러야 한다.** (시스템 핀 팝업은 호출한 앱 화면 위에 뜨므로, 앱을 백그라운드로 보내면 팝업이 사라진다.)

### 📌 일반 원칙 (어느 앱이든 그대로 적용)

1. **플랫폼 기능이 "안 된다" 싶으면, 빌드 반복·추측 전에 그 API의 계약서부터 읽어라.** 특히 콜백/리스너/PendingIntent가 *정확히 언제* 호출되는지(성공·실패·취소 시점).
2. **"OS/런처/기기/버전 때문"이라는 진단은 문서나 로그로 입증되기 전엔 입에 담지 마라.** 근거 없는 플랫폼 탓은 사용자에게 핑계로 들리고 신뢰를 깎는다.
3. **"X 직후 Y를 해야 한다"류 요구는 타이머·임의 delay·즉시 호출로 때우지 마라.** 플랫폼이 "X 완료"를 알려주는 **정식 훅(콜백)** 에서 Y를 하는 것이 경쟁 조건 없는 유일한 정답이다.
4. **시스템 UI(런처 핀 팝업, 권한 다이얼로그, 시스템 picker, 공유 시트 등)는 보통 호출한 앱/액티비티가 포그라운드에 있어야 표시된다.** 호출 직후 앱을 백그라운드로 보내면(HOME 점프, finish, 다른 Activity 시작 등) 그 UI가 사라진다.
5. **사용자는 코드를 안 읽는다.** 보고는 항상 "변경 트리 + 빌드 결과 + 설치 상태 + 검증 단계". 그래서 추측성 빌드 왕복은 특히 비싸다 — 코드를 짜기 전에 메커니즘을 먼저 확정해서 **한 번에 맞혀라.**

### ✔ 재사용 체크리스트 — 시스템/플랫폼 연동 기능 구현 "전"에

- [ ] 이 기능의 핵심 API 시그니처와 공식 문서를 실제로 읽었는가?
- [ ] 콜백/리스너가 **언제**(성공 시점 / 실패 시점 / 취소 시점) 호출되는지 명확히 아는가?
- [ ] "A 다음에 B" 요구라면, B를 거는 **정식 훅이 API에 이미 있는가?** 있으면 그것을 써라. `delay`/`postDelayed`로 때우지 마라.
- [ ] 이 호출이 **시스템 UI를 띄우는** 호출인가? 그렇다면 호출 후 앱을 포그라운드에 유지해야 하는가?
- [ ] "플랫폼/기기 때문"이라고 말하기 전에 **logcat 또는 공식 문서로 입증**했는가?
- [ ] 추측으로 빌드를 **2회 이상** 반복하고 있다면 → **멈추고** 메커니즘부터 다시 확정하라.
